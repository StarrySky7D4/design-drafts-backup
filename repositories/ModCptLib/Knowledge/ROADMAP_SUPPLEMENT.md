> **执行规则**：唯一可执行路线是 [`ROADMAP.md`](ROADMAP.md) 的 M0-M7。`agents_work/BOARD.md` 仅维护任务状态。本文的 N 标签、建议顺序和“近期动作”全部仅供检索与设计背景，不得据此领取或实现工作。

## 1. 保留的历史判断

原分析指出，身份、资源、联系人、群组、房间和发现的纵向设计之外，还需要贯穿所有阶段的闭环。这些问题仍应由 M0-M7 的明确 owner 处理，而不是形成平行路线：

| 历史缺口 | 现行接收阶段 | 约束 |
|---|---|---|
| 单一规范源、旧条款清理和协议登记 | M1 | `ROADMAP.md` 是执行路线；M1-02 是编号登记的唯一 owner。 |
| 可信变更、验证门和生成物漂移 | M0、M1 | 集成验证不能由任务分支的独立成功替代。 |
| Realm 服务端信任、降级和跨 realm 拒绝 | M2、M3 | M3 前不能产生可信产品会话。 |
| 一对一、群组、附件和 Room 的内容保密 | M2、M4、M6 | 签名或 HMAC 不是内容加密；未冻结算法不授权实现。 |
| 可靠投递、同步和本地数据生命周期 | M4、M5 | 必须定义确认、幂等、重试、恢复、导出和删除语义。 |
| 协议、schema、数据库和 FRB 生命周期 | M1、M2 | breaking、additive、behavioral 与 data-only 变更都要有版本和兼容结论。 |
| 可观测性、SDK 契约、供应链和发布 | M7 | 发布前需要稳定错误、取消、容量、SLO、SBOM 和回滚边界。 |
| 移动端/媒体工程、滥用治理 | M7 产品决策后 | 不是现有 Room 设计的隐含交付。 |

## 2. 已收敛的冲突结论

以下结论由身份与寻址 v2 模型和 M0-M7 路线约束；它们不是可选兼容策略：

| 历史冲突 | 现行结论 |
|---|---|
| `DeviceHello` 与 `IdentityFrame.publicKey` | principal 只能由 mTLS、credential evidence 和新 ALPN 的 `DeviceHello` 产生。旧 identity 类型返回 `UnsupportedProtocol`，自报公钥不能授权。 |
| “无公钥时未验证放行” | 认证材料不足或状态不可确认时 fail-closed；不建立未验证业务路径或 UI 降级授权。 |
| `(group_id, owner_uid)` | `GroupId` 单独全局唯一且由单一 genesis 绑定；owner 是可变群组状态。 |
| core 内 DHT relay 或 relay fallback | core 不实现 relay。未来外部 relay 仅能 `relay -> core`，须先完成 M7 产品边界决策。 |
| `UserId` 联系人视图 | UI 按 `UserId` 聚合；投递、授权、撤销和审计使用 `DeviceId`/`CredentialId`。 |

## 5. 内容安全的历史提醒

成员事件签名和消息签名只能说明来源或完整性，不能说明内容只有成员可读。在 M2-03 冻结并由后续阶段实现之前，“安全群组”不得被表述为端到端保密。尤其需要有唯一结论的场景包括：

- 首次会话、双方同时发起、乱序、丢消息、重试和幂等。
- nonce、associated data、replay、MessageId/TransferId 与 origin 的绑定。
- credential 轮换、设备撤销、新设备、历史恢复和备份。
- 群成员变更、Room epoch、媒体重放以及服务器、relay、mailbox 和本地存储可见的元数据。

这些是 M2 的决策输入，不是对任何现有线路、schema 或 Room 行为的承诺。
